# FAST-LIVO2 对应消息的坐标与边界

依据本次取得的 `LIVMapper.cpp` 修改及公开基线的周边代码说明。这是源码核对结果，不是本次重新运行结果。历史验收数字仍来自 [2026-09-01 报告](TEST_REPORT_20260901.md)。

## 消息格式

| 项目 | FAST-LIVO2 补丁的含义 |
|---|---|
| 话题 | `/pixel_point_correspondence` |
| 消息类型 | `sensor_msgs/msg/PointCloud2` |
| 字段 | `x,y,z,u,v,depth`，均为 FLOAT32，offset 为 0、4、8、12、16、20 |
| point_step | 24 字节 |
| xyz | FAST-LIVO2 世界坐标点 `p_w`，米 |
| header.frame_id | `camera_init` |
| u,v | 当前相机模型下的图像像素，重用上游 `w2c()` |
| depth | 当前相机坐标下的 Z，即 `w2f(p_w)[2]`；不是欧氏距离 |
| header.stamp | 最新测量中的 `vio_time`，经 `sec2Stamp()` 转换 |
| 发布条件 | 进入 VIO 分支、满足 `pub_scan_num` 条件，且通过筛选的对应点非空 |

`camera_init` 是算法初始化的世界参考，不自动等于导航系统的 `map`。对接地图或其他算法时，要检查真实 TF 与定位关系。

## 与独立 Python 投影脚本区分

| 来源 | xyz 坐标 | 消息帧 | 图像/点关联 |
|---|---|---|---|
| 本仓库独立 `lidar_camera_projection.py` | 原始 LiDAR xyz | 强制 `livox_frame` | 最新压缩图像 |
| 修改后的 FAST-LIVO2 mapper | 已在世界坐标的 xyz | `camera_init` | 重用融合程序当前视觉帧的投影 |

两者字段名相同、话题名相同，空间含义不同。一次运行只选择一个发布源。`colored_point_cloud.py` 会强制输出 `livox_frame`，因此不能直接订阅 mapper 的世界坐标对应消息，否则会给世界点贴上错误帧名。

不能对 mapper 输出的世界点直接再次应用 `p_C=R_CL*p_L+t_CL`，该等式的输入必须是 LiDAR 坐标。也不要把 `depth` 当成 LiDAR 的 x 或世界 z。

## 筛选与可视化

该实现沿用 mapper 彩色点云的筛选：跳过 `pf[2] < 0` 的点，检查图像内 3 像素边界，并要求 `pf.norm() > blind_rgb_points`。它没有新增统一的有限值检查，负深度条件本身也不拒绝零深度；消息合法性应由离线工具检查，不能由源码条件直接宣称所有输入下都满足正深度。

非空时才发布对应消息；某些帧没有消息不一定是节点崩溃，应同时检查 VIO 状态、发布间隔和有效点数。

`vio.cpp` 的红点来自视觉稀疏地图点选择过程，而对应消息是在世界彩色点云发布过程中生成，两者点集不能假定逐点完全相同。历史叠加图可用于观察投影，不能据此单独证明所有对应消息点都正确。

## 时间戳与下一步运行验收

补丁给对应消息使用 `vio_time`。上游 `publish_img_rgb()` 仍把 `/rgb_img` 的时间戳写成节点时钟 `now()`，本次补丁没有统一这两个时间来源。不要仅凭两话题频率接近，就认定消息头严格同步。新场景或回放时应核对时间戳、ROS 时钟设置和匹配规则。

这套补丁提供像素与世界点的接口和图像所有权修复，不包含目标检测、Mask、遮挡推断、逐点原始索引、语义地图或动态障碍物消除。新设备应用后仍需编译、运行和定量投影验收。
